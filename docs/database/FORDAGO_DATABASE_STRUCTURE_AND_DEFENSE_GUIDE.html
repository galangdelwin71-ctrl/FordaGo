5 Reasons This Database Passes Defense with Distinction

1Third Normal Form (3NF)

Walang redundant multi-value columns (1NF ✔), walang partial dependencies (2NF ✔), at walang transitive dependencies (3NF ✔). Bawat entity ay completely atomized.

2Referential Integrity Enforcement

Gumagamit ng FOREIGN KEY ... ON DELETE CASCADE sa InnoDB engine level — hindi lang sa application code. Kapag nabura ang user, awtomatikong nalinisan ang lahat ng kaugnay nitong records.

3B-Tree Indexing (Fast Queries)

Lahat ng foreign keys at madalas na hinahanap na columns (user_id, status, date) ay may explicit index. Gumagana sa O(log N) kaysa sa O(N) full table scan.

4ISO-Compliant Audit Trails

Bawat core table ay may created_at at updated_at timestamps para sa kumpletong data accountability at historical reporting.

5Modular Decoupled Architecture — 9 Independent Subsystems

Ang coaching module, attendance system, shop/POS, at chat module ay hiwalay na subsystems na konektado sa pamamagitan ng foreign keys. Dahil dito, scalable ang system — pwedeng dagdag ng bagong feature nang hindi sinisira ang dating data structure.

Master Defense Q&A Script

Naka-normalize ba ang database ninyo? Paano niyo mapapatunayan na 3NF ito?
Opo, Sir/Ma'am. Ang aming database ay mahigpit na sumusunod sa Third Normal Form (3NF). Kumpirmado po ito sa tatlong antas: Una, sa 1NF, bawat column ay atomic — walang multi-value o repeating groups. Pangalawa, sa 2NF, lahat ng non-key attributes ay fully functionally dependent sa buong Primary Key. At pangatlo, sa 3NF, tinanggal namin ang anumang transitive dependency — halimbawa, ang coaching rates at bio ng trainer ay nasa hiwalay na coach_profiles table at hindi kasama sa users table.
Paano ninyo pinipigilan ang pagkakaroon ng orphan records?
In-enforce po namin ang Referential Integrity gamit ang Foreign Keys na may ON DELETE CASCADE sa mismong MySQL InnoDB engine — hindi lang sa Laravel application code. Ibig sabihin, kapag nabura ang isang user account, awtomatiko at ligtas na lilinisin ng database engine ang lahat ng kaugnay na records tulad ng attendance, workouts, at notifications — nang hindi na kailangan pang gawin ito ng developer.
Bakit umabot sa 29 ang tables ng system ninyo?
Ang 29 tables po ay sumasalamin sa 9 na modular functional domains ng FordaGO: User Accounts, Gym Attendance & RFID/QR, Workouts & Personal Records, Equipment Tutorials, Coach Programs & Bookings, Real-Time Chat, Shop POS, Customer Feedback, at System Queue Infrastructure. Ang modular na disenyo na ito ay nagbibigay ng high maintainability at scalability — madali kaming makakapagdagdag ng bagong feature nang hindi binabago o sinisira ang lumang data structure.
Paano mabilis mag-query ang system kahit lumaki ang data?
Nagdagdag po kami ng explicit B-Tree Indexes sa lahat ng foreign keys at madalas na pinipintasan na columns tulad ng user_id, status, at date. Dahil dito, ang mga query ay gumagana sa O(log N) time complexity kaysa sa O(N) full table scan. Makikita po ito nang malinaw sa aming workouts table na may dedicated index sa user_id, at attendance table na may indexes sa user_id at check_in.
Saan nakalagay ang actual na database? Nakaprotektahan ba ito?
Ang database po namin ay nasa aming Cloud VPS na naka-host sa Singapore (168.144.141.27), tumatakbo sa loob ng isang isolated Podman container (fordago_db). Protektado ito ng firewall (UFW) at ang MySQL port (3306) ay naka-bind sa 127.0.0.1 lamang para hindi direktang accessible mula sa labas ng server. Ang lahat ng koneksyon ay dumadaan sa aming Laravel backend API na gumagamit ng hashed passwords (bcrypt) at Sanctum token authentication.
